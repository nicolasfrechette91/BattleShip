## Summary

1. **Same-machine replay determinism is strong, and the record proves it.**
   - About 70,000 lab dispatches had 0 prefix mismatches.
   - 3,916 inherited cells reproduced across runs.
   - 301 verified clears had 0 NONDETERMINISTIC verdicts.
   - Sources: `docs/frs_crossing_search_2026-10-15.md`, `docs/frs_crossing_search_run2_2026-10-15.md`.

   I found no mechanism that would make a fresh-process replay from tick 0 diverge on the same machine, executable and frozen
   configuration.
2. **The real determinism risk is portability.** On the MSVC build, decomp code that calls bare `sinf()`/`cosf()` goes to the
   host C runtime (ucrt) instead of libultra. Two consequences:
   - The Windows executable does not compute those values the way the N64 did.
   - Linux builds will disagree with Windows builds, because GCC and Clang route the same calls to libultra.

   One such site rotates **every weapon hitbox every frame**, including Mario's fireball. Measured here: libultra's trig differs
   from a correctly rounded result by exactly 1 ulp on **4 to 6 %** of all floats in [0.5, 8π]. The figure for ucrt specifically
   is the first thing to measure tomorrow (runbook step 4). This affects any BizHawk validation of the agent's words, any move to
   Linux headless training, and moves to another PC. **Finding D1.**
3. **Two run-killers or biases for a discovery-oriented search:**
   - A reply with a non-finite float (NaN or inf, plausible in a glitch) turns into an error stop of the whole run (D6).
   - The main process's selection is not reproducible: a stateful RNG, ingest in completion order, and first-come ties. Run-level
     A/B comparisons are noisier than they need to be (D4).
4. **Shortening: the decided run 3 is the right core.** That's the per-(level, mask) budget, the arrival-rank draw and decaying
   anchors. I recommend building it with four additions:
   - a fixed **breadth reserve** (an order-niche stream now, a discovery stream once the anomaly detector exists);
   - **deterministic scheduling**;
   - **non-finite-safe bursts**;
   - **bounded secondary representatives** behind a flag that is off by default.

   Putting the tick into the cell key is rejected (section 2.3). The segment optimiser stays tier 2.
5. **Throughput:** prefix replay is 86 to 93 % of all ticks, and process restart is 44 to 52 % of each ~4 s job [record]. In
   order of value per risk:
   1. persist end records (removes run 2's 14 % check overhead);
   2. the soft-reset pilot (C);
   3. the native batched prefix;
   4. incremental selection, which becomes the bottleneck once 2 and 3 land.

   Rendering is already gone. Audio and allocations are not worth attacking.

## 1. Determinism audit

### 1.1 What is already sound (checked, not assumed)

These were read in the code and found sound. They are listed so the risks below are not mistaken for the whole picture.

- **The tick contract.** One submitted action is consumed by exactly one native read. One update runs, and the host parks with
  no VRETRACE, so game time is frozen while parked [code: `port/rl/rl_step.cpp` header, `port/gameloop.cpp:763-801`]. The
  Python worker checks `consumed_tick == i`, `input_tick == i + 1` and the chain of canonical records on every tick
  [code: `rl/m8_rd_worker.py`, `rl/m8_rd_cells.py:210-240`].
- **Input edges come from netinput's own history, not from the pad.** Press and release are computed against the last
  *published* frame, which `syNetInputReset` clears at session start [code: `src/sys/netinput.c:256-271`, `:88-140`]. The
  physical controller is read first and then overwritten for every port [code: `src/sys/netinput.c:539-557`].
  - During the READY/GO wait the stock read runs [code: `src/sc/sc1pmode/sc1pbonusstage.c:101`]. The fighter's input is locked
    and zeroed at entry [code: `src/ft/ftparam.c:229-240`] until Go unlocks it [code: `src/if/ifcommon.c:2211`].
  - So a held pad or key does not leak into tick 0.
- **Controller enhancements are overwritten in stepping mode.** AnalogRemap, CStickSmash and DPadJump all act inside the stock
  read [code: `src/sys/controller.c:193-239`], so the publish overwrites their output for port 0.
- **Gameplay CVars are guarded.** TapJump and AutoZCancel act inside fighter code
  [code: `src/ft/ftcommon/ftcommonkneebend.c:94`, `ftcommonjumpaerial.c:271`, `ftcommonattackair.c:65`]. The session refuses a
  config that sets them [code: `rl/m8_rd_session.py:62,163-183`]. Each worker gets the frozen config by hash-checked copy
  [code: `rl/m8_rd_worker.py:115-140`].
- **Other per-frame enhancements don't reach BTT.** Stage-hazard disabling only applies to VS, 1P-game and training scenes
  [code: `port/enhancements/DisableStageHazards.cpp:10-12,203-219`]. Per-frame cheats only set unlock masks
  [code: `src/lb/lbbackup.c:241-257`].
- **Audio pacing is an integer error accumulator**, with no wall clock [code: `src/sys/audio.c:289-318`]. Audio output never
  blocks [record: `docs/rl_throughput_m6.md`, phase A].
- **Wall-clock reads stay out of game state.** The `osGetCount` reads feed diagnostics only [record: M6]. The per-60-frame
  timing log runs on the main thread, not the game fiber [code: `port/gameloop.cpp:946-952`]. `port_log` writes no timestamps
  [code: `port/port_log.c`].
- **The anti-piracy save flags are neutralised under PORT.** These flags change physics: half stick range at
  `src/ft/ftmain.c:1452` and random knockback at `src/ft/ftparam.c:1625`. Their DMEM/IMEM checks report OK under PORT
  [code: `src/sys/main.c:140-165`]. Each episode also gets its own fresh save path [code: `rl/battleship_process.py:238`].
- **Observation capture zero-fills its structs**, and the diagnostic blocks travel under one lock with their observation
  [code: `port/rl/rl_observation.cpp:53-150`, `port/rl/rl_step.cpp:611-645`]. The transport thread only reads latched copies.
- **JSON is exact and locale-independent.** nlohmann (`port/rl/rl_transport.cpp:136`) round-trips floats exactly. Python
  canonicalises with `allow_nan=False` [code: `rl/m8_rd_cells.py:218`].
- **Burst words are keyed SHA-256 draws**, not a stateful generator [code: `rl/m8_rd_explore.py`], and each lab burst is
  re-derived from its keys at the close [code: `rl/frs_run.py` header].
- **Workers are isolated.** Each has a private runtime directory: config copies and a junction to `.tcc` only, with a ROM probe
  refusal [code: `rl/m7_runtime.py:58-68,146-200`].
- **Hash-ordered containers in the port bridge don't affect game memory.** They are iterated only to evict by range, which
  doesn't depend on order [code: `port/bridge/lbreloc_byteswap.cpp:1061-1080`, `port/port_aobj_fixup.cpp:328-345`].
- **Empirical:** 0 prefix mismatches, 0 tick-0 differences and 0 quarantines over about 70,000 dispatches; 0 NONDETERMINISTIC
  verdicts in 301 double replays [record, the two crossing-search records].

#### D1 (HIGH, cross-build): host libm trig in gameplay on MSVC

- **Code.** libultra's `sinf.c` and `cosf.c` alias the bare names with `#pragma weak sinf = __sinf`. CMake documents that "MSVC
  ignores the pragma; those sites keep host libm there" [code: `CMakeLists.txt:674-681`]. On GCC and Clang the alias holds, so a
  Linux or macOS build uses libultra, like the N64. Bare call sites on gameplay paths:
  - `src/sys/vector.c:130-131` (`syVectorRotate3D`) and `:183-184` (the rotate-about-axis helper).
  - `src/wp/wpprocess.c:18`: `wpProcessUpdateHitOffsets` rotates **every weapon hitbox offset by the weapon's spin, every frame**.
    Mario's fireball spins, so its hitbox positions go through ucrt on Windows.
  - `src/ft/ftphysics.c:430`: TransN animation velocity (Ness and Yoshi double jumps; not Mario).
  - The Ness up-B and reflector paths through `syVectorRotate3D` and `syVectorRotateAbout3D` [code: grep in `src/ft`, `src/wp`].
- **Measured here** [measured here: `tools/audit/trig_ulp_check`, every float in each range, GCC 13 and Clang 18 give identical
  results]:

  | range | floats | libultra sinf ≠ correctly rounded | libultra cosf ≠ correctly rounded | sinf ≠ glibc | cosf ≠ glibc | differences > 1 ulp |
  | --- | ---: | ---: | ---: | ---: | ---: | ---: |
  | [1e-6, 0.5) | 158,976,067 | 0.57 % | 4.25 % | 0.38 % | 4.25 % | 0 |
  | [0.5, π) | 21,565,403 | 5.17 % | 4.60 % | 5.71 % | 4.68 % | 0 |
  | [π, 2π) | 8,388,608 | 4.71 % | 5.11 % | 4.80 % | 5.22 % | 0 |
  | [2π, 8π) | 16,777,216 | 4.94 % | 4.91 % | 5.00 % | 4.99 % | 0 |

  libultra's polynomial is off by exactly one ulp on about one input in twenty. **I did not measure ucrt** (no MSVC here). If ucrt
  is near correctly rounded, as modern libms are, the Windows port disagrees with the N64 on about 5 % of these trig calls
  [unverified until runbook step 4].
- **A second Windows-only effect** [unverified]. The MSVC CRT documents `_set_FMA3_enable` because its x64 transcendental routines
  pick an FMA3 code path when the CPU has it, and results may differ in the last bit. So one executable could give different
  results on two Windows CPUs. The harness measures this with `/DTRIG_FMA3_TOGGLE` (runbook step 4b).
- **Scenario.**
  - A fireball whose hitbox just touches a target on the Windows build misses by one ulp on the N64, or on a Linux build.
  - The clear then fails its BizHawk replay, which the handoff requires for any original-game result. It also fails a future
    Linux headless worker's prefix check, or behaves differently on another PC.
  - Searches seek razor-thin contacts by construction, so "one ulp rarely matters" is weak comfort.
  - On one machine and one executable it is deterministic, which matches the record.
- **Fix options (decision O3).**
  - (a) A PORT-only, MSVC-only forced-include header for the `ssb64_game` target: `#define sinf __sinf` and `#define cosf __cosf`.
    That matches the N64 and Linux. It changes the executable, so every archive and claim must be re-checked; prefix checks
    quarantine whatever changed.
  - (b) Keep ucrt, declare "Windows x64, ucrt, this CPU" the reference platform, and call `_set_FMA3_enable(0)` at startup to
    remove the CPU dependence. That also changes results wherever FMA3 was on.
  - (c) Do nothing and never mix builds or machines.
- **Local tests.**
  - Runbook step 4 (ucrt against libultra: this decides whether D1 is real on Windows).
  - Later, a native A/B replay of the 1,245 and the 1,885 on a build with option (a), counting the ticks at which the chain first
    differs. It needs your authorisation.

#### D3 (LOW, cross-worker): port race and anonymous transport

- **Code.**
  - `allocate_loopback_port()` binds port 0, reads the port and **closes the reservation before the child binds it**
    [code: `rl/battleship_process.py:205-219`; its docstring calls the window "unavoidable"].
  - The native side listens with a backlog of 1 and serves one client at a time [code: `port/rl/rl_transport.cpp:806`].
  - `status` returns state, step count and flags, but no process identity [code: `:422-458`].
- **Scenario.** Two standbys boot at once, and A and B are handed the same free port.
  - A's child binds; B's child fails to bind and runs on without a transport.
  - B's client connects to A's child first and sees a fresh episode. A's client waits in the backlog and fails at startup.
    A's cleanup then terminates the child that B is stepping.
  - That ends in lifecycle failures, never in a wrong record (same executable and config). A verify-flag client attached to an
    explore-flag child would fail on missing diagnostic blocks.
  - The one unexplained startup `transport_failure` in M6's scaling sweep ("status request failed before a fresh episode was
    established; process still alive", `docs/rl_throughput_m6.md` §scaling) fits this pattern [unverified].
- **Fix.** The Python side passes a nonce, `SSB64_RL_LAUNCH_NONCE`, and the native `status` echoes it with the process id
  (additive fields, PORT-only). The client refuses a mismatch. Or the child binds port 0 itself and writes the port into its
  private episode directory, which removes the race. Bundle it with the next native build (decision O5).
- **Local test.** Zero-tick, with the fake game: start two fake children forced to the same port and assert that the launcher
  refuses the identity mismatch. Natively, the same with two real processes.

#### D4 (MEDIUM, research validity): the search is not reproducible run to run

- **Code.**
  - Selection draws come from one `random.Random(rng_seed)` in the main process [code: `tools/frs/crossing_search.py:131,830`,
    drawn in `select` at `:392` and `select2` in run 2].
  - Results are ingested in completion order, which follows the wall clock.
  - Equal-tick arrivals keep the first one ingested (`if tick >= c.tick: LATER`) [code: `:332`].
  - Continuation answers read the archive at the moment a boundary question arrives.
  - A worker stops waiting for an answer after 60 s of wall time [code: `rl/frs_worker.py:36,225`].
- **Scenario.** Replays are unaffected: words are recorded and burst words are keyed. But two runs of the same configuration
  diverge after the first out-of-order completion. That costs three things:
  - "common random numbers" between arms (planned for lab night 1, `docs/frs_lab_index.md`) are not achievable;
  - an arm difference mixes the arm effect with scheduling noise;
  - an anomaly cannot be re-found by re-running the search.
- **Fix (in run 3, Python only).**
  - Keyed selection draws: `<archive id>|run3|select|<dispatch index>`, the scheme `rl/m8_rd_explore.py` already uses.
  - Deterministic ingest: dispatch *i* is selected from the archive after ingesting exactly results 0 … *i* − *D* − 1, with a
    reorder window *D* = 2 × workers. The main loop waits only when a straggler holds the window.
  - Tie-break equal ticks by `(tick, words_digest)`.
  - Answer continuation questions from the same lagged view.
  - The result is a function of (archive, parameters, worker count), not of timing.
- **Local test.** Zero-tick: run the run-3 search on the stub backend twice with randomised job latencies and assert that the
  final archive digests are identical. Run it with *D* = 0 to show the test detects the current behaviour.

#### D5 (LOW): the reset hotkey and console in worker windows

- **Code.** Ctrl+R (libultraship's GUI) and the ESC-menu reset dispatch the `reset` console command, which calls
  `portSCManagerRequestReset()` [code: `port/port.cpp:595-618`, `port/gui/Menu.cpp:895-912`, `src/sc/scmanager.c:1991`].
- **Scenario.** Someone types into a focused worker window during an unattended run. The scene ends at the next unparked frame.
  The worker sees the episode end early: a false "fall" for that burst, or a contract violation and a lifecycle failure. It can
  never produce a false clear.
- **Fix.** Refuse `reset` while RL stepping is in effect (PORT-only). This is the same scene-manager hook family as (C), so it
  lands in the (C) build.
- **Local test.** Send `reset` through the console in a stepping process; expect a refusal line and an unchanged chain.

#### D6 (MEDIUM, discovery): non-finite floats stop the run

- **Code.**
  - nlohmann serialises NaN and inf as JSON `null`.
  - `cell_key` does `float(o["position_x"])` [code: `rl/m8_rd_cells.py:184`], which raises `TypeError` on `None`. The record's
    canonical form would raise `ValueError` on a real NaN (`:218`).
  - `run_job` maps any other exception to `kind: "error"`, "surfaced by the runner as an error stop" [code: `rl/frs_worker.py:210`].
- **Verified here:** `cell_key` with `position_x = None` raises `TypeError: float() argument must be a string or a real number,
  not 'NoneType'` [measured here].
- **Scenario.** A burst reaches a degenerate state. A zero-length collision normal or a division in physics yields a non-finite
  position or velocity. The whole lab run stops, at exactly the event a glitch hunt wants to keep.
- **Fix.**
  - In run 3's worker wrapper (not in `m8_rd_cells.py`), check the reply for `null` in the numeric fields before keying.
  - On one, end the burst cleanly as an `anomaly: nonfinite` event: words kept, the native trace preserved, the cell not keyed.
  - Mark the cell for an immediate fresh-process replay from tick 0. The anomaly counts only if it reproduces (addendum part 4).
- **Local test.** Zero-tick: a stub-world reply with `null` in a position field must end the burst as `nonfinite` and keep the
  run running.

#### D7 (LOW, latent): uninitialised locals in decomp code

- **Measured here.** `tools/audit/uninit_scan.sh` compiled 171 gameplay files in PORT mode with clang 18: 0 compile failures and
  72 candidate paths. Output: `build-audit/uninit_scan.txt`, git-ignored.
- **Triaged on Mario's paths:**
  - `src/ft/ftcommon/ftcommonjumpaerial.c:206`: only the Kirby and Purin cases set `status_id`, in the multi-jump setter. Not
    reachable for Mario.
  - `src/ft/ftcommon/ftcommonwalk.c:54`: an exhaustive switch over the three walk statuses.
  - `src/mp/mpprocess.c:463`: `result` is unset only if the loop runs zero times. That needs `is_coll_end` already TRUE on entry,
    but fighters and weapons reset it each tick before the call (`src/ft/ftmain.c:1969`, `src/wp/wpprocess.c:187`).
  - `src/sys/vector.c:153-155`: unset only for an axis other than X, Y or Z.
  - The rest are untriaged and mostly display or interface code.
- **Why it still matters.**
  - The port already met this class of bug: an OSMesg union whose high bytes held a stack pointer [code: `port/gameloop.cpp:88-108`].
  - On PC, an uninitialised stack slot holds whatever an earlier call left. When that was a pointer, the value changes with ASLR
    on every process.
  - Two fresh-process replays from the same parent with the same environment tend to share most garbage, so they are a weak test
    for this.
  - New glitch routes reach code the 1,245 never did.
- **Local test (strong, cheap, outside the shipping executable):** a pattern-initialised differential build.
  - Build the US executable twice with clang-cl, once with `-ftrivial-auto-var-init=pattern` and once with `=zero`. The shipping
    MSVC executable is untouched.
  - Replay the 1,885, the 1,245 and the scripted baseline on both builds and compare the chains.
  - Any difference is a reachable uninitialised read on that route, located by the first differing tick.
  - It needs a non-shipping build and your authorisation for native replays (decision O8).

#### D8 (LOW, diagnostics): native anomalies are invisible during lab runs

- **Code.** Two native-only events exist:
  - the controller read reached in an unexpected state: a fallback park in the game coroutine, which costs one extra VRETRACE and
    so a `time_passed` step out of line with the input tick [code: `port/rl/rl_step.cpp:557-587`];
  - a step needing two host frames [code: `:652-658`].

  Both go only to `port_log`. Every process opens `%APPDATA%\BattleShip\ssb64.log` with mode `"w"` [code:
  `port/port.cpp:1257-1273`, `port/port_log.c:9-12`]. So with five workers and their standbys, each boot truncates the others'
  logs, and a bind failure, the only trace of D3, is lost.
- **Mitigated:** `time_passed` is in the record, so the chain and verification catch any such event that changes a claim.
- **Fix.** Additive `status` counters (`fallback_parks`, `multi_frame_steps`) that the worker asserts are 0 at every job end,
  plus a per-process log path (`SSB64_LOG_PATH`, set per episode by `battleship_process.py`). PORT-only, with the next native
  build (O5).
- **Local test.** The counters' zero-tick test with the fake game; natively, the existing regressions plus one job.

#### D9 (LOW): the frame count before tick 0 is not pinned

- **Code.** The tick-0 record pins the observation without `host_frame`, the spatial blocks and the collision-line digest
  [code: `rl/m8_rd_cells.py:210-230`]. The frames run before Go are deliberately excluded as a process-lifetime counter. In a
  fresh process they should be a constant.
- **Scenario.** Any boot-path dependence (asset loading that waits, a scheduler stall) changes how many frames ran before tick 0.
  The pinned record might still match while hidden per-frame state differs.
- **Fix.** Record `host_frame` at tick 0 as an informational pin, reported but not part of the chain, and alarm on change. It
  reads no RNG and changes no contract.
- **Local test.** `tools/audit/tick0_frame_probe.py`: ten fresh boots; every tick-0 `host_frame` must be equal (runbook
  step 9, needs your authorisation). Against the fake game it reports "not constant", as it should, because the fake counts frames
  by wall time.

#### D10 (LOW): the CVar guard is a deny-list

- **Code.** `CONTROLLER_CVAR_NAMES = ("tapjumpdisabled", "autozcancel", "failedzcancelflash")` [code: `rl/m8_rd_session.py:62`].
  That covers every gameplay-reaching CVar today (section 1.1). A future PORT hook in fighter or map code would not be covered.
- **Fix.** An allow-list test: grep every `port_enhancement_*` and `CVarGet*` call reachable from `decomp/src/{ft,gr,it,wp,mp,gm}`
  and from `sc1pbonusstage.c`, and require each such CVar to be absent or default in the frozen config. The test fails when a new
  call site appears. A zero-tick suite item.

#### D11 (MEDIUM for any Linux build): FP contraction

- **Code.** `-ffp-contract=off` is applied only to `sinf.c` and `cosf.c` [code: `CMakeLists.txt:682-688`]. GCC in GNU C mode
  defaults to `-ffp-contract=fast`. On x86-64 without FMA target flags nothing is fused today, but an `-march=native` or
  `x86-64-v3` build, or AArch64, which CMake's own comment names, would fuse `a*b+c` throughout the game. MSVC with the default
  `/fp:precise` doesn't contract.
- **Fix.** `-ffp-contract=off` for every `ssb64_game` C source on non-MSVC. It doesn't change the Windows executable. Do it
  before any Linux headless worker is trusted (O9).
- **Local test.** Build the Linux port twice, once with `-march=x86-64-v3` and once without, and replay; or diff the
  disassembly for `vfmadd`.

#### D12 (LOW): claims are verified on the stepping path only

- `frs_verify` replays through `m7f_trace.run_stepping_trace` with the verify flags [code: `rl/frs_verify.py` header]. The native
  text-replay path (`SSB64_BTT_INPUT`), which btti and bk2 exports and the video use, is covered by the M1e and M6 regressions
  in general but not per claim.
- **Fix.** For each new best only, one native text replay of the canonical words as a third check, comparing completion clocks.
  It costs one boot. Decision O7.

#### D13, D14 (INFO)

- No gameplay path found from a physical pad, the keyboard or a Raphnet adapter during stepping (section 1.1). Keep the Raphnet
  bypass for throughput.
- Save data: fresh per episode. To make "fresh SRAM" explicit, assert before launch that the episode's `SSB64_SAVE_PATH` doesn't
  exist (`port/port_save.cpp:73-80` zero-fills a missing file).

### 1.3 Threads, floats, I/O and containers: the rest of the checklist

- **Threads.** The game runs as fibers on the main thread. The transport worker touches only latched copies under one mutex. The
  game fiber takes that mutex for a few instructions and never across a yield [code: `port/rl/rl_step.cpp` header, `:538-590`].
  The watchdog only reads counters. The updater and shader-downloader threads don't touch game memory. No data race on game state
  was found.
- **Float order.** There are no parallel reductions in game code. MSVC `/fp:precise` and GCC without fast-math don't reassociate.
  The remaining float risks are D1 and D11. MXCSR: fibers are created without `FIBER_FLAG_FLOAT_SWITCH`
  [code: `port/coroutine_win32.cpp:139`], so a library that changed MXCSR on the main thread (FTZ or DAZ) would change game floats.
  Nothing in the port does so; a cheap assertion is to log MXCSR at tick 0 (O9).
- **I/O and real time in the loop.** Per-frame `port_log` calls (every 60 frames) and per-boot log and config writes only; no
  wall-clock reads into game state (section 1.1).
- **Unordered iteration.** Python: archive sets are of `int`, whose hashes aren't randomised; `levels_present` is sorted. Native:
  eviction-only iteration (section 1.1). The real ordering problem is D4, which is about time, not hashing.

## 2. Clear-shortening design

### 2.1 Where the line stands [record]

- **Best verified:** 1,245 ticks. 37 % of it is slow or waiting: landing lag, helpless falls, idle, down-B and fireball phases.
- **Chaining the agent's fastest observed segments gives about 860, and nothing below about 850.** Those segments come from
  different lineages (`docs/frs_strategy_2026-10-16.md` §1, §2).
- **The bottleneck is returning to good states, not the inputs.**
  - The 1,245's chain used 13 of 39,309 dispatches. Each link produced the next within its first three dispatches but waited 267
    to 4,596 dispatches to be drawn.
  - 72 to 82 % of faster replacements were never dispatched (§5).
- **Already decided** (`docs/rl_decisions_2026-10-16.md`):
  - tier 1 = the run 3 tool (end records stored, a per-(level, mask) budget, an arrival-rank draw with a novelty floor, anchors
    per class that halve without progress);
  - then the order-diverse right-side arm;
  - state-aware representatives only if that stops;
  - tier 2 = the segment optimiser.
- **Open:** the discovery track (addendum part 4).

### 2.2 Requirements for the shortening explorer

- **Minimise `completion_input_tick`** over clears verified from tick 0. Claims are replayed only when faster (decided Q10).
- **Keep the phase-1 contracts unchanged:** cell key `m8_rd_cell_v1`, record, chain and Track 1. Any new archive behaviour is
  additive, behind flags, and off unless stated.
- **Stay broad enough to find new routes or glitches,** not only polish the 1,245 family.
- **Rules stay generic:** archive quantities only, no coordinates, ids, census numbers or routes.
- **Make runs reproducible** (D4) and robust to anomalies (D6).

### 2.3 Approaches compared

| | A. Time-to-beat Go-Explore (run 3 plus additions) | B. Time-bucketed cells | C. Segment optimiser (tier 2) |
| --- | --- | --- | --- |
| cell identity | phase-1 key unchanged | key + ⌊tick / Δ⌋ | start states = anchor prefixes; a segment ends at the next break |

**Rejected outright:**

- learned policies (M7 and M9 collapsed: `docs/rl_m9_g3_stop_review_2026-10-10.md`);
- changing the explorer's word distribution (the fastest segments are near-uniform draws, §5 of the strategy review);
- any savestate-based branching (out of scope by decision).

### 2.4 Recommendation: A, with B in bounded form and C later

- **Why A.**
  - The evidence says the scarce resource is dispatches of the right states, and A attacks exactly that.
  - It needs no native work, reads run 2's archive unchanged, and keeps every contract.
  - It is the decided stage 0 and 1, so no decision is re-opened.
- **What A lacks**, which the four additions supply:
  - (1) a guaranteed breadth budget, since the anchor mechanism pulls everything toward the incumbent lineage;
  - (2) reproducibility (D4);
  - (3) anomaly safety (D6);
  - (4) a way to keep "the state that crossed" when a faster but different arrival evicts it. That is option 4 of the strategy
    review, built here as a bounded secondary-representative slot behind a flag, off for night 1.
- **Why not B as a key.** B keeps every slower variant as identity. The records show the problem is *dispatching* the right states
  more often, not *having* them: 3,334 of 9,069 level-7 cells were never dispatched (§5). B would multiply undispatched cells. The
  useful part of B, not evicting a materially different state, is addition (4) at a fraction of the cells.
- **Why C later.** It polishes one route family and is boot-bound today. It becomes cheap after (C) and the batched prefix
  (section 3). It stays tier 2 at the first checkpoint, as decided.

### 2.5 Cell definition (unchanged identity, time-aware treatment)

- **Identity** stays `m8_rd_cell_v1`: (⌊x/300⌋, ⌊y/300⌋, resource class, live-target mask, floor line if grounded). Level =
  targets broken.
- **Time enters in three places, none of them the key:**
  1. **Group rank.** Within a group *g* = (level, mask), each cell's arrival tick has a rank r ∈ {0, 1, …} (0 = earliest).
  2. **E7 bound.** Cells with L > best verified − margin − 1 are ineligible: the registered rule `record_bound_max_L`, as in run 2.
  3. **Anchors.** The *k* = 3 earliest arrivals per (group, class), with *class* = the resource class (decided Q5), plus each
     anchor's descendants' earliest arrivals at the next level.
- **Addition (4), flag `--secondary-reps`, off by default.** Per key, up to *m* = 2 extra representatives, distinguished by a
  generic sub-key from fields the record already holds:
  - the sign of x velocity, the sign of y velocity and facing;
  - for grounded cells, the moving group's direction (the sign of its speed in `spatial.groups`), which is generic: every stage's
    moving groups expose it.

  A faster arrival replaces only within its sub-key. These slots get no anchor share and draw only from the novelty-floor part of
  the group's budget. Turned on at stage 3 per the decided order, or earlier if you say so (O6).

### 2.6 Selection and scoring

All draws are keyed (D4). Per dispatch:

1. **Stream.**
   - With probability 0.80: exploitation (steps 2 to 4).
   - With probability 0.10: the **order-niche stream**.
   - With probability 0.10: the **discovery stream** (until the anomaly detector exists, this 10 % goes to the order-niche stream).
2. **Level.** Run 2's level weights (decay 0.5 from the deepest live level), unchanged.
3. **Group within the level.**
   - share_g ∝ max(φ, ρ_g), with ρ_g = (b_g + e_g + 1) / (n_g + 2) over the group's last W = 200 dispatches:
     - b = breaks,
     - e = new earliest arrivals at the next level,
     - n = dispatches.
   - The floor is φ = 1 / (4 · groups at the level).
   - Decided Q2 and Q11. A 0-break group falls to the floor and no longer takes 8,078 dispatches.
4. **Cell within the group.**
   - The anchor share s_g, starting at 0.5, halves after each anchor burst without a new earliest arrival in the group and resets
     on one (decided Q4).
   - An anchor draw picks the anchor with the most lead.
   - Otherwise: weight = (1 + r)^−α × max(ν, (1 + fresh)^−1) × cleared factor, with α = 1 and ν = 0.05.
5. **Order-niche stream.**
   - Niche = (level, order prefix of broken targets). The order is derived generically from the cell's lineage mask history,
     which the archive stores.
   - Uniform over niches that have at least one eligible cell. Within a niche, the earliest arrival 50 % of the time, otherwise
     uniform.
   - This is decided stage 2's mechanism, always on at a small share, so stage 1 never loses order diversity entirely.
6. **Discovery stream** (after addendum part 4 is decided).
   - Weight cells by the rarity of the anomaly signatures their bursts produced: position jumps beyond the largest per-tick
     displacement seen so far at that level, a collision line crossed between ticks, a status transition never seen before, and
     non-finite values (D6).
   - Rarity = 1 / (1 + count of that signature).
   - Every anomaly is replayed from tick 0 before it counts.

**Objective and claims.**

- The E7 bound is tied to the best verified clear and tightens with every new best.
- Claims are replayed only when faster (decided Q10).
- Each verified best is appended to `best_times.jsonl`: tick, words digest, chain, both replay verdicts, and the btti or bk2 path
  once exported.
- Stopping follows the plateau rule (decided Q11).

### 2.7 How breadth survives

- A fixed 20 % reserve that the exploitation terms cannot absorb (step 1).
- The group floor φ means no (level, mask) group starves, including masks with an early-left order.
- Novelty floor ν: every eligible cell keeps a nonzero chance.
- Optional secondary representatives (flag): materially different states are not evicted by a faster arrival.
- Anomaly safety (D6): the first glitch doesn't end the night.
- Reproducibility (D4): an anomaly or a new order seen once can be re-found by re-running with the same keys.

## 3. Throughput review

### 3.1 Where the time goes [record: `docs/frs_prefix_cost_2026-10-14.md` §2, `docs/rl_throughput_m6.md`]

| level | measurement |
| --- | --- |
| native frame (no-render, Raphnet bypass) | 0.28 ms of a loaded 1.1 to 1.4 ms tick. Event pump, VI rotation, scheduler round, controller read, game update (0.03 ms), audio, display-list build; the display-list walk and present are skipped. |
| round trip per tick | 65 to 75 % of a loaded tick: four thread handoffs (Python → transport thread → main thread → transport thread → Python), JSON build (1,408 B, of which spatial is 914) and parse |
| Python per tick | 57 µs: parse 29.5, record digest 29.9, checks and chain < 5 |
| unloaded N = 1 | 0.45 ms per step, 2,112 ticks/s. N = 5 aggregate 8,273 steps/s without boots. |
| per job (about 4.0 s) | prefix stepping 41 to 48 %, burst 3 to 5 %, standby wait 18 to 22 %, outside the job clock 27 to 30 % (close, transfer, ingest, selection 53 to 82 ms, verification borrow) |
| per run | prefix = 86 to 93 % of ticks. Run 2: 3,916 re-checks of inherited cells = 19,772 lent-worker-s = **13.9 %** of five workers over 28,505 s. |
| boot | 2.04 s unloaded, 3.76 s median under load. About 85 % is process and runtime initialisation, which no in-process mechanism avoids. |

So the hot loop is not the game: a native frame is under a quarter of a tick. The cost of returning to a cell (boot plus prefix)
is more than 90 % of all work, and the burst that actually explores is 3 to 5 %.

### 3.2 The per-step hot loop, item by item

- **Rendering:** gone in no-render mode. The display list is still built by the game (it must be, the game is unchanged) and
  discarded unwalked [code: `port/gameloop.cpp:902-907`]. Nothing left to gain.
- **Audio:** synthesis runs every frame (CPU ADPCM and mixing) inside the 0.28 ms frame. Skipping it would change sound-player
  lifetimes. They are read by gameplay only to stop sounds (D2), but the gain is small, it changes the executable, and it needs the
  full equivalence suite. **Not recommended.**
- **Allocations and copies:**
  - Native: an nlohmann JSON tree per reply (dozens of small heap allocations) and three struct copies under the mutex.
  - Python: one parse and one canonical dump per tick.
  - Measured together inside the 57 µs (Python) and the round trip (native). Worth attacking only through batching (item 3
    below), not piecemeal.
- **Logging:** one line per 60 unparked frames. Negligible.
- **Synchronisation:**
  - Per tick: four context switches, which is the dominant cost under load.
  - Between workers: the single-threaded main process does selection (53 to 82 ms per dispatch, growing with cells), continuation
    answers, ingest (0.34 ms) and verification scheduling. It is fine at about 1.3 dispatches/s today and saturates at about 10/s
    (item 4 below).
- **Physical input polling:** part of the 0.23 ms before the read in each frame is the controller thread's SDL and keyboard read
  (`docs/rl_throughput_m6.md`, follow-up: "the remaining 0.23 ms is the scheduler round, the message pump, vblank and the
  controller thread's keyboard / SDL read"). Port 0 is overwritten in stepping mode (section 1.1), so a PORT flag could skip the
  device read entirely.
- **Boot extras:** the menu fires the update check when it loads [code: `port/gui/PortMenu.cpp:1711-1717`]. That shells out
  through `Updater.cpp:251` once per process: five workers plus standbys, every few seconds, each spawning a process and touching
  the network. Cost unmeasured; verify by process monitoring during a boot (runbook step 8).
